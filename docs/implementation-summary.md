# 技術實作總結（v2）

> 由實際程式碼與資料庫狀態整理；數字見 `docs/generated/pipeline-stats.md`（`python scripts/generate_docs.py` 產生）。
> 核心問題：**怎麼把官方網站上各種領域的非結構化補助公告，轉成電腦可以判斷「這個人符不符合、值不值得申請」的結構化資料，而且每個值都能指回原文？**

## 與 v1 的差異

| 項目 | v1 | v2 |
| --- | --- | --- |
| 資料庫 | SQLite / PostgreSQL（SQLAlchemy） | MongoDB（Docker），文件即 schema |
| 領域 | 教育（獎學金） | 教育、青年、社會福利、長期照顧、身心障礙、勞工、住宅、醫療（taxonomy.yaml，資料可擴充） |
| 來源 | 7 個 | 24 個（含 source.xlsx 的 51 個網址：HTML、PDF、CSV/JSON/XML、略過項記錄原因） |
| 關鍵字 | 人工維護 keyword_rules.yaml | 由語料統計產生 keyword_rules_v2.yaml（log-odds ratio），附完整報告 |
| 條件抽取 | 固定欄位 + 每個領域手寫 regex | 屬性登錄表（YAML）+ 通用型態規則（數值／布林／有序 enum／縣市／身分）+ 條件句對屬性 |
| LLM | 雲端（Anthropic/OpenAI/Gemini）可選 | 只用本地 Ollama（qwen2.5:7b），填空缺、對條件句、判複雜條件、解析使用者描述 |
| 媒合 | 規則引擎 + 缺欄位追問 | 硬過濾候選 + 規則引擎（推定不拒絕）+ 資訊增益追問 + 排序漏斗（需求／時效／成本／互斥組合） |
| 前端 | 資料中心／我的獎學金 | 資料中心（含原始文件與略過原因）／屬性登錄表／我的補助（需求類型、三張卡、建議組合） |

## 不造假的機制

1. 來源驗證：網域白名單 + HTTPS + 標題關鍵字；blocklist 記錄非官方網址（銀行登入頁）。
2. 原文保存：raw_documents 存原文與 hash；data/raw 存完整 HTML。
3. 摘錄驗證：規則、給付特徵、AI 填的值都必須附原文摘錄，validator 用去空白子字串比對確認；數值必須出現在摘錄。
4. 屬性白名單：規則的 attribute_id 必須在登錄表；AI 提議的新屬性只進審核佇列。
5. 推定標記：「本市」→ 機關縣市為 inferred，不能造成不符合。
6. 缺資料 = unknown：不會判不符合；彙整頁不逐條產規則。
7. AI 紀錄：每筆 benefit 的 llm.accepted / rejected / errors 可在資料中心看到。

## 關鍵決策

- **關鍵字來自語料**：以有類別標籤的頁面為正例、名單／統計／網站結構頁為負例，算 z 分數，再以 lift、跨來源、非縣市名等條件過濾掉公文常用詞與版面字；門檻用語料回測校正；種子詞只在統計不足的類別中保留並標記。
- **規則式優先、AI 補位**：規則式抽取只做高精確度的句型；例外句（但／惟）、過長句、一句多條件 → 交給 AI；AI 對不到 → complex（顯示「需進一步確認」）。
- **登錄表成長、程式不變**：新增領域 = 加屬性與類別到 YAML；rule engine 依型態判斷。
- **排序與資格分開**：先用規則判資格，再依需求類型套權重算適合度；互斥條款用來做組合而不是扣分。

## 已知限制與下一步

- 類別關鍵字：長照／勞工／住宅等類別的標記文件仍少，多數類別以種子詞為主；持續爬取後重跑 `--mine-keywords`。
- 只有附件沒有內文的方案頁會被過濾（附件內容不抓）；門檻校正是訓練語料上的自我評估。
- 7B 模型對條件句的屬性對應有時保守（回 null）；可換更大的本地模型（`LLM_MODEL`）或增加候選屬性描述。
- `poverty_line.yaml` 需填官方最低生活費後才能推導「所得倍數」。
- 追問只依資訊增益，不含第 10 節的「偏好題」；回饋資料尚未用來校正權重。
