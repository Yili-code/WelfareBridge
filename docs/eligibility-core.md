# 資格骨幹與分層媒合

目標：**篩出真的符合的人，但不能漏掉**。舊引擎逐條套用抽取出來的規則，只要一條「可拒絕」規則不符就整筆隱藏；規則抽錯（「本縣」推成別的縣市、加碼身分當成必要身分、條列擇一變成全部都要）時，符合的人就看不到。資料不足的補助也一律隱藏。

## 做法

### 1. 資格骨幹（`backend/app/services/core_builder.py`）

每筆補助只保留少數「決定誰能申請」的條件（facet），存在 `benefits.eligibility_core`：

| 種類 | 內容 |
| --- | --- |
| `residence` | 限定縣市（空＝全國）與依據：設籍／居住／擇一／就讀學校所在地 |
| `age` | 受補助者年齡範圍；`via_child` 表示家長代子女申請 |
| `education`、`student` | 限定學制、須在學 |
| `identity_any`、`identity_exclude` | 至少具備其一的身分、具備即不符的身分 |
| `nationality`、`attr` | 國籍；失業、租屋、需長照、主要照顧者、性別等 |

每種條件由多個**獨立來源**投票，每個來源最多一票：

- `structure`：發布機關層級與轄區，以及類別（獎學金類＝須在學）
- `title`：標題中的縣市、身分、學制、年齡、兒少字樣
- `text`：原文的「設籍本市」「年滿65歲以上之老人」「辦理求職登記」等句型
- `rules`：抽取管線的 simple 規則（非推定、信心 ≥ 0.8）
- `llm`：本地 AI（`CORE_LLM_MODEL`，預設 qwen3:8b）。每個值都要附原文引用；引用不在原文、身分引用句沒提到該身分、年齡數字對不上引用句的，一律丟棄

投票規則：

- 兩個以上來源一致 → `confirmed`，只有這種能讓媒合隱藏補助
- 只有本地 AI 一票的身分、學制、其他條件不採用（黃金集回測 9 成是錯的）；只有抽取規則一票且 AI 有跑的也不採用
- 身分排除若原文排除的是「已領其他補助者」（領取…補助者、安置費補助者），不算身分排除
- 身分所在的那一行與上下行並列多種申請對象（…之老人／一般戶獨居老人／遊民），且相鄰行沒提到該身分 → 視為擇一
- 特殊境遇家庭各項扶助在申請時一併認定，不以已具特境身分為前提
- 標題寫「學生、就學、學雜費、獎學金、助學金」→ 須在學一票（幼兒園、學前、托育除外）；原文「入國小前、學齡前」不是學制條件
- 方案名稱本身的「減免／免費」（學雜費減免）不算加碼語氣；標題括號裡的「低收免費」仍算
- 條件句語氣檢查（`caveat`）：句中有「優先、免費、加發、下列之一、或（另有非身分選項）、條列其中一款、每人每月補助…（給付項目說明）」→ 降為 `uncertain`。標題本身寫明對象時，「或／之一」這類擇一語氣不降級，「優先／加碼」仍降級
- 標題「低收入戶救助」這類申請取得身分本身的頁面，身分不作為前提
- 同票數互相矛盾且其中一方是「全國」：那一票來自標題／發布機關（中央機關）時，不設戶籍限制；**只有本地 AI 說全國時保留縣市限制但降為 `uncertain`**（縣市機關發布、原文沒寫「設籍本縣」時 AI 常判成全國，整條刪掉會讓別縣市的人看到 ✅）

### 2. 分層（`backend/app/matching/engine.py`、`eligibility_core.py`）

| 分層 | 條件 | 顯示 |
| --- | --- | --- |
| ✅ 符合（`tier1`，`high_match`） | 沒有任何條件不符；已確認、多來源、戶籍、兒少類條件都已比對相符；至少一項有鑑別力（全國、單純「須在學」不算） | 首頁「符合」區 |
| 🟡 可能符合・需補充資料（`tier2`，`possible_match`） | 沒有已確認的不符，但有條件缺資料，或只有未確認的條件不符 | 列出 `needs_labels`（要補哪些欄位），未確認的不符標「公告條件未完全確認」並排後面；戶籍縣市與使用者不同時，比對原因列「限設籍○○（公告寫法不完全明確，請向承辦單位確認）」 |
| 不顯示（`hidden`，`not_match`） | 已確認的條件不符，或骨幹以外屬性的可拒絕規則不符 | 媒合診斷可看原因 |

有骨幹時，骨幹涵蓋的屬性（戶籍、年齡、學制、身分、國籍、就業、租屋、長照）的逐條規則不再單獨排除，只在「不符合的條件」與已確認的骨幹一致時照實列出。沒有骨幹的舊資料沿用舊邏輯。

### 3. 問卷 → 媒合資料（`src/lib/benefit-profile.ts` 的 `toMatchingProfile`）

首頁比對、媒合診斷與聊天小幫手都使用。小幫手問到的資料存在 `profile.assistantAttributes`，最後套用、優先於問卷推得的值（從對話內容判讀的保持「未確認」）。

- 年齡只選區間時送 `preferences.number_ranges`，以範圍比對
- 「家庭經濟困難」→ 清寒；「經濟大致穩定」→ 非清寒
- 身分題有作答時，未勾選的原住民、身障證明（本人與家人）、單親／特境家庭視為不具備；勾選身障（可能是家人）不推定本人
- 工作狀態只有一個明確選項才送；居住方式、需長照、主要照顧者依選項送

Python 版 `backend/scripts/eval_matching.py::to_matching_profile` 必須同步修改。

## 分類資料修復（`backend/scripts/repair_classification.py`）

- 去重加上轄區判斷：不同縣市的同名方案不再合併（原本 12 個縣市的「弱勢家庭兒童及少年緊急生活扶助」併在金門縣一筆底下）。重跑後主要紀錄 1,126 → 1,351，可媒合 1,032 → 1,250
- 機關欄抽成「林社工為您服務」等字樣的縣市政府來源補上轄區（36 筆；抽取器也已改為以來源機關補轄區）
- 分類待確認的 13 筆交給本地 AI 重判：3 筆判定不是補助而移除、3 筆確認、7 筆仍待人工
- 抽取器合併互斥身分群組時只合併經濟身分（低收／中低收／清寒），老人、原住民等維持必要條件
- 保留集抽樣另發現 4/30 筆不是個人可申請的方案：衛福部 e 寶箱入口頁、「脫貧自立 3+1」政策說明、耐震弱層補強（被分成學雜費減免）、已停辦的優惠購屋貸款

## 回測

標註檔都在 `data/gold/matching/`，由 Claude 逐筆閱讀官方原文標註：

- `benefit_facets.yaml`（125 筆）：**用來調整規則**，數字偏樂觀
- `holdout_facets.yaml`（30 筆，26 筆計分）：隨機抽樣，標註時未看系統輸出；看過它的失敗案例後修了一條通用規則（排除「已領其他補助者」不是身分排除），因此已不算完全乾淨
- `holdout2_facets.yaml`（20 筆，17 筆計分）：所有調整完成後才抽樣，**只評估一次、沒有據以調整**，是最誠實的數字
- `personas.yaml`：30 位使用者

2026-09-16 跨縣市檢查：以「戶籍基隆」的使用者實測，✅ 區出現彰化縣低收入戶補助、桃園市低收及中低收促進就業服務——原因是本地 AI 把縣市頁面判成「全國」，同票數下整條戶籍限制被刪掉。改成只有 AI 說全國時保留限制並降為 `uncertain` 後，三個縣市的 ✅ 區都不再有別縣市方案，回測漏掉率不變。

2026-09-16 覆核：對照系統抽取結果逐筆檢查分歧，只依原文判斷。修正 8 筆標註（職訓生活津貼與失業給付補上須為失業者；4 筆特境扶助頁移除「已具特境身分」；基隆轉載的衛福部要點改標全國；鹿港天后宮清寒獎助學金補上清寒；前一天另補上中華開發技藝職能獎學金的 30 歲以下），確認 6 筆標註正確而系統錯誤。修正紀錄寫在各筆的 `note`。

## 已知限制

- **縣市頁面上的全國方案、非設籍者條款**：發布機關與標題都是某縣市時會被確認為限該縣市（例如嘉義縣住宿式服務機構使用者補助其實向機構所在縣市申請；臺北市急難救助另有非設籍者條款）。去重修正後其他縣市的使用者通常看得到自己縣市的版本，但跨縣市的人仍可能漏掉
- **別縣市的方案仍會出現在 🟡**：戶籍限制只有「發布機關」一個來源（原文沒寫設籍）時不確認，因此不隱藏。以基隆／高雄／臺東三位使用者實測，✅ 區沒有別縣市的方案，🟡 約 250 筆中有 76～83 筆屬於別縣市，其中 9 成已標示「此方案可能限設籍○○」並排在同層最後；其餘是真的全國方案（衛福部帳戶、轉知僑委會獎學金、榮民就養給付等）
- **🟡 清單偏長**：首頁問卷資料少，許多補助只能列「需補充」；依缺少欄位數排序，首頁只顯示前幾筆
- **兒少方案**：不知道有沒有未成年子女時一律列 🟡；問卷的「扶養未成年子女」選項還沒轉成子女資料
- **本地 AI**：qwen3:8b 在 RTX 3070 約 5 秒／筆，偶爾輸出過長被截斷（該筆只用規則式訊號）。換更大的模型後用 `--refresh-llm` 重跑，再跑回測比較
- **分類待確認的紀錄不進媒合**：三方投票不一致（含本地 AI 不在線）時標 `classification.uncertain`，`load_records` 會整筆排除。
  2026-09-16 整站重爬時模型忙不過來，62 筆已確認的補助被降級而整批消失（黃金集漏掉率一度 17.2%）。
  已加上「AI 不在線時沿用先前判斷」的保護（`pipeline.keep_prior_classification`），但**真正不一致的紀錄仍然完全看不到**——
  與「只有已確認的資格不符才隱藏」的原則不一致，建議改成進 🟡 並標示「資料待確認」
- 標註由 Claude 閱讀原文並覆核，仍建議人工抽查（抽查頁：https://claude.ai/artifact/TKEFt74Xk4w8wVbbekcjzm）；修正紀錄見各筆 `note`
- **金額仍有少數是門檻或預算總額**：全庫 95 筆金額範圍跨度超過 100 倍（多為「每月 4,164 元～每年 25 萬元」這種把年度上限與月補助混在一起），
  另有 3 筆是方案年度預算（獎學金每年 500 萬元上限）或諮詢門檻。金額只影響顯示與排序，不影響資格判斷
- 分類面仍有非方案頁進入媒合（例如「臺灣省及福建省低收入戶生活扶助金額表」會被列為符合），需要在收錄政策補上金額表、統計頁的判斷
- 「誤推」偏高的主因是首頁問卷資料少、許多條件只能列 🟡；兒少方案在不知道有沒有子女時一律列 🟡

## 指令

```powershell
docker compose run --rm --no-deps benefit_crawler python scripts/build_eligibility_core.py            # 建立骨幹
docker compose run --rm --no-deps benefit_crawler python scripts/eval_matching.py --details 10        # 回測（調整用黃金集）
docker compose run --rm --no-deps benefit_crawler python scripts/eval_matching.py --labels holdout2_facets   # 保留集二
docker compose run --rm --no-deps benefit_crawler python scripts/eval_matching.py --core rebuild      # 用目前程式在記憶體重算骨幹（不寫入）
docker compose run --rm --no-deps benefit_crawler python scripts/build_eligibility_core.py --gold --report --details  # 各類條件抽取準確度
```
